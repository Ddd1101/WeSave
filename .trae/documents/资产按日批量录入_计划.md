# 资产按日批量录入 · 实施计划

目标描述：

1. **数据库现有数据没有日期** → 补齐今天的日期（`2026-06-09`）作为所有资产的基线快照日期；
2. **以“天”为单位，一次表单保存当天全部资产**（不再一条一条点击新增/编辑）；
3. **打开表单时，以当前已有最新一天的资产快照为预填数据**，用户可以微调；
4. **已经输入过的日期也允许再次打开并修改**（重新保存该天的快照）。

---

## 1. 现状调研

数据库（`Server/data/assets.db`）已有两张表：

- `assets`：当前资产主表（包含 `category / name / value / purchase_date / purchase_price / remark / created_at / updated_at`），**缺少“快照日期”字段**。
- `asset_history`：资产变更历史表（`asset_id / action / snapshot_date / category / name / value / purchase_date / purchase_price / remark / change_amount / recorded_at`），已具备 `snapshot_date` 维度。

`seed.js` 写入基线历史时 `snapshot_date = todayStr()`，因此新库有日期，但若 `assets` 表中的历史数据是之前手工录入或其他途径写入的，就可能没有对应的 `asset_history` 快照行，需要补齐。

后端路由（`Server/src/routes/assets.js`）当前提供：

- `GET  /assets` → 返回 `assets` 主表（不带日期概念）
- `POST /assets` → 新增一条资产
- `PUT  /assets/:id` → 更新一条资产
- `DELETE /assets/:id` → 删除一条资产
- `GET  /assets/snapshot?date=YYYY-MM-DD` → 返回某天快照（历史表，若无且 date=today 则 fallback 到主表）
- `GET  /assets/snapshots` → 区间趋势
- `GET  /assets/:id/history` → 单资产历史
- `GET  /assets/changes` → 变更聚合

前端页面：

- `Page/src/pages/AssetTable.vue`：当前资产列表 + 汇总卡片；调用 `listAssets()`（无日期维度）。
- `Page/src/components/AssetForm.vue`：单条资产新增/编辑弹窗。
- `Page/src/pages/SnapshotTable.vue`：按日期查看历史快照（只读表格 + 饼图/柱图）。
- `Page/src/pages/Trends.vue`：按日期区间查看趋势折线图。

## 2. 数据模型设计（向后兼容）

核心思路：**以 `asset_history` 表为主数据视图**，`assets` 表保留为“最新条目”缓存，供简单列表查询。

本次不改动 schema（两表字段已足够），但调整语义：

- `asset_history.snapshot_date` 是用户录入的“某一天日期”（`YYYY-MM-DD`）；
- `asset_history.action` 的取值由原来的 `create/update/delete/snapshot`，统一为：
  - `snapshot`：用户对某一天完整保存一次（批量录入/修改）时的资产值；
  - `manual_override`：旧的单项新增/修改（保留兼容，但 UI 不再作为主入口）。
- 同一天对同一资产若多次批量保存，允许覆盖：后端 `POST /assets/batch-snapshot` 会先 **DELETE 该日期的历史记录，再一次性插入所有资产**。
- `assets` 主表在每次 `POST /assets/batch-snapshot` 提交的日期为“今天”时，同步 upsert，其他日期只写历史表，不改动主表。

> 这样「最新一天 = 最新主表」的假设成立，其他日期的查询都走 `asset_history` 表。

### 数据唯一性约束

由于 better-sqlite3 未加约束，需要在业务层保证：

- `GET /assets/snapshot?date=D` → 取到该日期下每个 `asset_id` 的最后一条记录；
- `POST /assets/batch-snapshot?date=D` → 删除 `snapshot_date = D` 的旧行，插入新行；
- `change_amount` = 当前值 − 上一日期（按 `snapshot_date < D`）该资产的最后一次值（首次出现时为 `NULL` 或 `value`）。

## 3. 后端改动清单

### 3.1 补今日基线（一次性迁移脚本）

新建 `Server/scripts/patch_today_snapshot.js`：

- 读取 `assets` 表当前所有资产；
- 以 `todayStr()` 作为 `snapshot_date`；
- 检查 `asset_history` 中是否已有该日期的 snapshot 记录；
- 若没有：逐条写入一条 `action = 'snapshot'` 的历史记录，`change_amount = null`；
- 输出结果，用户执行一次即可。

### 3.2 新增 `GET /assets/dates`

返回已录入过快照的所有日期列表（升序），用于前端日期选择器的“已录入日期高亮”。

```text
GET /assets/dates
Response:
{
  "dates": ["2026-06-01", "2026-06-05", "2026-06-09"]
}
```

SQL：`SELECT DISTINCT snapshot_date AS date FROM asset_history ORDER BY date DESC`。

### 3.3 新增 `POST /assets/batch-snapshot`（核心接口）

参数：

- `query.date`：必填，快照日期（`YYYY-MM-DD`）；
- `body.assets`：资产数组，每一项字段 `{ id?, category, name, value, purchase_date?, purchase_price?, remark? }`。

逻辑：

1. 校验 `date` 格式，校验 `assets` 中每项的 `category/name/value`；
2. 开始事务：
   - `DELETE FROM asset_history WHERE snapshot_date = ? AND action = 'snapshot'`
   - 对每一项资产：
     - 若资产 `id` 已存在于主表，执行 `UPDATE assets SET value=?, purchase_date=?, purchase_price=?, remark=?, updated_at=CURRENT_TIMESTAMP WHERE id=?`（仅当 `date === todayStr()`）；
     - 若资产 `id` 不存在或该日期的新资产：`INSERT INTO assets ... RETURNING id`；
     - 取上一日期该资产的最后一条 `value`：
       ```sql
       SELECT value FROM asset_history
       WHERE asset_id = ? AND snapshot_date < ? AND action = 'snapshot'
       ORDER BY snapshot_date DESC, recorded_at DESC LIMIT 1
       ```
       有则 `change_amount = newValue - prevValue`；否则 `change_amount = newValue`。
     - `INSERT INTO asset_history (asset_id, action='snapshot', snapshot_date=?, ...)`
3. 提交事务，返回 `{ date, assets, total, by_category }`（与 `/assets/snapshot` 相同的格式，便于前端直接刷新）。

> 说明：当用户在编辑“今天的资产”并保存时，会同时覆盖 `assets` 主表 + `asset_history` 的今天快照；当用户编辑的是历史日期，仅覆盖 `asset_history`，不改主表。这样“最新日期” ≈ “主表” 的假设保持成立。

### 3.4 调整 `/assets/snapshot`

- 取消“今日 fallback 到主表”的逻辑，改为直接从 `asset_history` 读取；
- 若某天完全没数据，返回 `{ date, assets: [], total: 0, by_category: [] }`；
- 读取方式：对每个 `asset_id` 取 `snapshot_date = ? AND action = 'snapshot'` 的行（`action = 'snapshot'` 已在提交时保证该日期唯一）。

### 3.5 `recordHistory` 函数保留

保留给单项 CRUD 调用（历史日期编辑流程不再走它），`action = 'manual_override'` 以示区分。

## 5. 数据补全 & 验证步骤

1. 执行 `node Server/scripts/patch_today_snapshot.js` 为现有资产补一条 `2026-06-09` 的 `snapshot` 基线。
2. 验证：
   - `GET /assets/snapshot?date=2026-06-09` 返回 19 条资产 + 总额；
   - `GET /assets/dates` 返回 `["2026-06-09"]`。
3. 在页面上打开“批量录入”，随意修改某项价值为 99999 并提交，再次 `GET /assets/snapshot?date=2026-06-09` 能看到新值；`GET /assets/changes?start=2026-06-09&end=2026-06-09` 能看到 `change_amount = 99999 − 原值`。
4. 重选另一个历史日期（如 `2026-06-01`），保存后再回到 `2026-06-09` 查看，两条日期的数据彼此独立。

## 6. 风险与兜底

- **旧表与历史表语义冲突**：历史上可能已有 `action = 'create' / 'update'` 的旧记录；新的 `/assets/snapshot` 只读 `action = 'snapshot'`，避免污染。
- **删除某条资产的入口**：保留原 `DELETE /assets/:id`，同时在批量表单中提供“空行”（不写 `id`）/“删除行”按钮；删除行仅影响本次日期的历史记录，不会删除主表中的资产（避免误伤）。
- **事务**：`better-sqlite3` 通过 `db.exec("BEGIN")` / `COMMIT` / `ROLLBACK` 手动管理，`POST /assets/batch-snapshot` 务必保证原子性。
- **空数据库兜底**：首次启动且无任何历史数据时，`GET /assets/snapshot` 会返回空数组；前端 `AssetTable.vue` 会提示“请点击「批量录入今日资产」”，而不是报错。
